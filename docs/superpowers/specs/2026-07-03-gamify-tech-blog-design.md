# 技术博客游戏化学习系统 — 设计文档

日期：2026-07-03
状态：已确认（用户批准）

## 1. 目标与定位

把一篇技术博客（10-30 分钟的被动阅读）转化为 5-10 分钟的可玩游戏，让读者通过主动决策快速掌握文章核心知识，并将通关后的知识归档为可检索、可再互动的个人知识库，形成「阅读 → 游戏 → 归档 → 复习」的闭环。

- **定位**：个人工具，单用户，无账号体系、无分享功能。
- **理论依据**：提取练习（retrieval practice）——主动从记忆中提取知识的留存率远高于被动重读。游戏机制强迫玩家做真实的技术判断，天然实现提取练习。
- **成功标准**：贴入一个博客 URL，2 分钟内生成可玩的游戏；通关后自动生成知识笔记；旧笔记可通过挑战卡再互动。

## 2. 整体架构：五段流水线

```
博客 URL
   │
   ▼
[1] 抓取与清洗 ──── Readability 抽正文，保留代码块与图片
   │                 （架构图作为视觉输入喂给 LLM）
   ▼
[2] LLM 分析器 ──── 产出「知识档案」(knowledge profile)：
   │                 • 文章分类（架构/概念/复盘/工具）
   │                 • 概念图谱（概念、依赖关系）
   │                 • 关键决策点（作者的权衡与理由）
   │                 • 常见误区（出题素材）
   ▼
[3] 游戏编译器 ──── 按分类路由到玩法模板，产出「游戏谱」(game spec JSON)
   │
   ▼
[4] 游戏运行时 ──── 玩家游玩，记录每个决策（对/错/玩家理由）
   │
   ▼
[5] 归档器 ──────── 生成知识笔记 → SQLite 存储 + Obsidian Markdown 导出
```

**核心设计决策：游戏谱（game spec）是声明式中间产物。** 一份 JSON Schema 约束的文档，描述场景、选项、正确答案与解析；游戏引擎只是它的渲染器。收益：

- LLM 输出可校验（Schema 校验失败可重试），远比让 LLM 生成可执行代码可靠；
- 游戏可重玩、可调试——出问题直接看谱、改谱；
- 同一份谱未来可被不同引擎渲染。

## 3. 文章分类与玩法映射

| 文章类型 | 玩法 | 机制 |
|---|---|---|
| 系统架构 / 工程实践 | **决策冒险** | 玩家扮演当事工程师，在关键节点做选择，展示后果，最终与作者真实决策对照。答案不是对错，而是思路对照。 |
| 故障复盘 / postmortem | **侦探解谜** | 先给症状（图表、日志摘录），玩家花费有限的「线索预算」申请查看线索，提出根因假设，再揭示真实结论。预算机制模拟 on-call 的优先级排序。 |
| 概念 / 原理讲解 | **预测闯关** | 把推导切成台阶，每步先让玩家预测「接下来会怎样」再揭示。 |
| 新技术 / 工具介绍 | **快问快答** | 知识密度低的文章不硬凑剧情：5 道场景判断题，2 分钟速通。 |

## 4. 游戏引擎

### MVP：一个场景图运行时 + 四种玩法编排

场景图 = 节点（情境描述、提问、选择、揭示、线索）+ 边（选择走向）。四种玩法是同一运行时上的四种节点编排风格与视觉皮肤。借鉴叙事引擎（Ink/Twine）的内容与执行分离思路。

### 演进方向：四个独立引擎（用户明确要求）

MVP 之后，四种玩法各自演进为独立引擎，拥有专属的交互形态与视觉语言（例如侦探解谜获得证物板/连线推理界面，预测闯关获得逐步动画推演）。场景图运行时保留为共享基础设施，游戏谱 Schema 按引擎分化为方言。

## 5. 知识归档与再互动

### 归档内容（通关后自动生成）

- 核心要点（3-5 条）
- 概念图谱
- 玩家决策记录：做对/做错的题、玩家当时的理由
- 原文链接与元数据

### 双出口

1. **应用内知识库**（主存储，SQLite）：可搜索、按主题聚合；每道错题生成一张「挑战卡」。
2. **Obsidian Markdown 导出**：带 frontmatter（来源、日期、标签）与 `[[概念]]` 双链，一键写入 vault。

### 再互动机制

- **挑战模式（可跳过）**：打开旧笔记时先出现一张当年的挑战卡，可点击跳过直接看笔记。答对间隔拉长、答错重新入队（简化间隔重复）。
- **今日挑战**：知识库首页从到期挑战卡中抽 3 张，2 分钟热身。
- **跨文章连击**（Phase 2）：新文章的概念图谱与旧笔记重叠时，游戏中插入一道回顾题，钉合新旧知识。

## 6. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | Next.js (App Router) + TypeScript + Tailwind | 本地运行，前后端一体 |
| 数据库 | SQLite + Drizzle ORM | 本地零配置；日后上 Vercel/Neon 只换驱动 |
| LLM | Claude API（claude-fable-5） | 长文理解 + Schema 约束的结构化输出；架构图走视觉输入 |
| 正文抽取 | @mozilla/readability + jsdom | 成熟稳定 |

运行形态：本地 Web 应用（`npm run dev` / build 后本地启动），数据私有。

## 7. 分阶段计划

- **Phase 1（MVP）**：五段流水线 + 场景图运行时（四种玩法编排）+ 应用内知识库 + 挑战卡（可跳过）+ 今日挑战 + Obsidian 导出。
- **Phase 2**：四玩法拆分为独立引擎（含架构拼图：拖拽组件搭架构、注入故障验证）；跨文章连击。
- **Phase 3**：自由生成兑底——模板都不合适的文章，由 LLM 现场生成自包含 HTML 小游戏，在 sandbox iframe 中运行。

## 8. 错误处理

- 抓取失败 / 反爬：提示用户手动粘贴正文作为替代输入。
- LLM 输出不符合游戏谱 Schema：自动重试（附校验错误信息），连续失败则降级为快问快答玩法。
- 文章过长：分段摘要后再进入分析器。

## 9. 测试策略

- 游戏谱 Schema 校验与场景图运行时用单元测试覆盖（图遍历、计分、状态机）。
- 流水线端到端：用 3-4 篇固定文章（每类一篇）做金样本回归。
- LLM 输出质量靠 Schema 校验 + 金样本人工评估，不做自动断言。
